# COMPATIBILITY: API Stability & Versioning Contract

This document defines the **compatibility contract** of RTICX:

- the **platform API**: the public surface that other crates (in-tree
  distributions, out-of-tree distribution repositories, external
  compilation-pass authors, and the user code generated by the `#[…::app]`
  macros) compile and link against; and
- the **versioning scheme** that expresses changes to that surface.

It defines *policy*, not signatures. The authoritative reference for exact
signatures is the source code itself (rustdoc + `cargo-semver-checks`); this
document defines what may change, how it may change, how it is versioned, and
who must be notified when it does.

## What is frozen

The public surface of the following modules constitutes the platform API:

| Area | Location |
|------|----------|
| Core backend trait | `rticx-core/src/backend.rs` (`CorePassBackend`) |
| Pass/pipeline API | `rticx-core/src/lib.rs` (`RticPass`, `RticMacroBuilder`, `MainInjections`) |
| Info bus | `rticx-core/src/info_bus.rs` (`InfoBus`) + the `INFO_*` keys published by each pass |
| Attribute parsing | `rticx-core/src/parse_utils/mod.rs` (`RticAttr`) |
| Software-task backend trait | `compilation-passes/rticx-sw-pass/src/lib.rs` (`SwPassBackend`) |
| Async-task backend trait | `compilation-passes/rticx-async-pass/src/lib.rs` (`AsyncPassBackend`) |
| User-facing syntax | the parser modules of `rticx-core` and of each compilation pass (`#[app]` args, `#[task]`/`#[sw_task]`/async task attributes, `#[shared]`, `#[local]`, `spawn`/`spawn_by`/`cross_spawn`, ...etc) |
| Distribution `export` contract | `src/export.rs` of each distribution (re-exports generated code relies on: `Queue`, `pend`, `lock`, `run`, critical-section helpers, async runtime path) |

Anything outside these modules is an internal implementation detail and may
change freely.

## Stability rules

1. **Additive only.** New capabilities are introduced via:
   - new *defaulted* trait methods
   - new optional syntax keys.
   Direct changes to existing signatures, removals, or semantics changes of
   existing items are **forbidden** outside a breaking release.
2. **Deprecation cycle.** When an item must eventually go away: introduce the
   replacement additively, mark the old item `#[deprecated]`, keep it working
   for at least one minor release, then remove it in the next breaking minor.
3. **Breaking change = coordinated cone.** A breaking change requires a
   generation bump (see Versioning) and all in-tree backends are updated in
   the same PR. Out-of-tree distributions (their own repositories / git
   submodules) get follow-up PRs *after* the release; existing consumers
   stay on the previous minor via caret requirements.
4. **Syntax is additive only.** Passes must strip the arguments they consume
   before returning from `run_pass`; unknown `#[app]` arguments produce
   warnings, never hard errors (existing convention).
5. **Generated-code contract.** The items documented as re-exported by a
   distribution's `export` module are part of the contract for that
   distribution's generated code. Changing them is a breaking change for
   that distribution.

## Versioning

### Generation model (0.x)

All crates of the **root workspace** (the core crates, the passes, the
cortex-m distribution pair, and the tools) share one **generation**: the
major.minor pair of their version, and own their **micro** (patch) version
individually:

```
generation  0.2      shared by every root-workspace crate (CI-enforced)
micro       0.2.x    bumped per crate
```

- **Micro (patch) bump**: non-breaking changes. Bumped crate-by-crate
  (`0.2.0` → `0.2.1`). Dependent crates pick it up automatically via caret
  requirements; no coordinated re-release needed.
- **Generation (minor) bump**: breaking changes only. All root-workspace
  crates move to the new minor **together, in a single PR** (`0.2.x` →
  `0.3.0`). This turns the coordinated-cone rule into a hard gate:
  `make check-versions` (and the `version-check` CI workflow) fail until every
  root-workspace crate shares the new generation.
- **Major (1.0)**: reserved for a future stable release of the framework.

### Distribution pairs

The riscv and rp2040 distributions live in their own mini-workspaces
(pending their move to separate repositories). Their distro crate and macro
crate **inherit one locked version** from their workspace manifest
(`version.workspace = true`), so the pair always moves together and is
published at the same version.

### Consumer impact

- Consumers depend on crates with caret requirements (`rticx-core = "0.2"`):
  micro patches flow in automatically; a new generation is only picked up
  when the consumer (or their distribution) opts into it.
- Out-of-tree distributions opt into a new generation via follow-up PRs
  after the core release (see Change procedure).

## Change procedure

### Adding a capability (non-breaking)

1. Add the defaulted method / optional syntax key.
2. Document it in the trait's rustdoc (contract, porting notes) and the wiki.
3. Semver outcome: micro (patch) bump of that crate only.

### Making a breaking change

1. Justify: the change must be impossible via the additive/deprecation path.
2. Do it in one PR that updates the crate **and every in-tree backend**
   (cortex-m distro; any in-tree passes) **and bumps the generation of every
   root-workspace crate**. CI, QEMU, `make check-versions`, and the publish
   dry-run must be green before merge.
3. Release via the normal release-PR flow. Review the `cargo-semver-checks`
   report: it must show the expected incompatibilities and nothing
   unexpected.
4. After the release, open follow-up PRs in the out-of-tree distribution
   repositories (riscv, rp2040, …) bumping their dependency requirements and
   updating their backends. Their release-plz publishes independently.

## Enforcement

- `make check-versions` / the `version-check` CI workflow: fails when any two
  root-workspace crates disagree on major.minor (generation).
- `cargo-semver-checks` runs on every release PR for all host-buildable
  crates (configured in `release-plz.toml`) and is the mechanical guarantee
  for API compatibility.
- Human checklist for any PR touching the modules listed above:
  - [ ] Change is additive (defaulted method / new optional key)?
        If not, it follows the breaking-change procedure.
  - [ ] All in-tree backends updated in the same PR.
  - [ ] Generation bumped across all root-workspace crates when breaking.
  - [ ] No changes to existing signatures or generated-code contracts.
